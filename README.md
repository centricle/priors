# priors

What four Claude models reach for when told to improve a black circle.

The write-up, with every finding, is at
[centricle.com/curios/priors](https://centricle.com/curios/priors/). This
repository holds the runner, the tasks, every output, every counted transcript
from the room, the tallies, the renders and the site. The findings are not
restated here.

## What this is

Give a model a bare black circle and the single word "improve", many times, and
look at what it reaches for. Then do the same with a near-empty HTML page, an
empty SVG and a one-word sentence; ask for a number, a digit and a word with no
file at all; and ask it to replicate a page. A second campaign, a week later,
asked for a color ten ways.

Four models, pinned by full id: `claude-haiku-4-5-20251001`, `claude-sonnet-5`,
`claude-opus-5-5` and `claude-fable-5-1`. Every trial ran inside the Claude Code
CLI at version 2.1.283, so the subject is the model inside that harness, not the
model alone. What the harness adds is tabled below.

| | Trials | Runs | Dates |
|---|---|---|---|
| First campaign, `campaign.tsv` | 2,608 | 41 | 2026-09-27 and 2026-09-28 |
| Second campaign, `campaign-2.tsv` | 3,792 | 42 | 2026-10-04 |
| Total | 6,400 | 83 | |

A trial is one `claude -p` process. A *sample* run is n independent trials from
the same seed. A *chain* run feeds each trial's output to the next, 64 steps
deep. The pilot that started this, 32 trials run by hand, is imported as
`runs/pilot-import/` and tallied alongside the first campaign without being
counted in it.

## The room

Every counted trial is one `claude -p` process, launched in a fresh directory
under the system temp directory that holds only its input: the seed file, the
previous step's output in a chain, or nothing for a question. On macOS `/tmp`
is a link to `/private/tmp`, so the path the model sees is
`/private/tmp/<room>`, where the room is a fixed five-letter name per task
(`tasks/<task>/room`). The directory is not a git repository, on purpose: the
pilot's trials shared one, and read each other's commit messages.

The launch:

```
claude --safe-mode --strict-mcp-config --tools Read,Write,Edit,Bash --restricted \
  --settings '{"attribution":{"commit":"","pr":""}}' \
  --model <id> --effort low \
  --permission-mode acceptEdits --permission-prompts none \
  --session-id <uuid> \
  --output-format stream-json --verbose \
  -p "<prompt>"
```

- `--safe-mode` drops user instruction files, hooks, skills, memory and MCP
  servers. `--strict-mcp-config` ignores every MCP configuration not passed on
  the command line, and none is.
- `--tools Read,Write,Edit,Bash` pins the surface. Glob and Grep are not
  offered, matching the CLI's default surface at this version.
- `--restricted` confines the file tools to the working directory and ignores
  project settings a model might write. Reads and writes outside it, `env`,
  `curl`, `open` and starting a server are all denied. Read-only shell commands
  inside the directory still run.
- The attribution setting stops the CLI from asking the model to sign commits
  with a trailer, which would otherwise be the only instruction in the room
  beyond the harness's standing guidance.
- `--effort low` on every trial, for every model. Effort is recorded nowhere in
  the session record on this version, so the argument is the only proof of it.
- One session id per trial, never reused. The session record is hashed against
  a golden record for its model: the system prompt, the tools and whatever is
  attached before the first reply. A trial that differs is halted and retried,
  and the halted attempt is recorded but not counted. The CLI binary is hashed
  too, and the runner stops if it changes mid-campaign.

This is not a stock install. It is more bare than one. What the model is still
told: an environment block (working directory, platform, shell, OS version, the
fact that it is not a git repository), the date, its own model name and id with
a knowledge cutoff, the account's email address, a token budget line (dropped
for Fable and Opus in the second campaign), and the harness's standing guidance
about how to behave as a coding agent.

One run is the exception. The 32 trials of the harness replica,
`runs/replica-harness-haiku-low/`, launch the way the pilot did, with the full
user configuration, plus a session id and stream-json output so they can be
recorded. Their records are hashed against a golden too, but a mismatch is
recorded, not halted. Their transcripts are not published; see below.

## What the harness injects

A bare call to the Messages API with no system prompt carries none of what
follows. The CLI adds all of it before the model sees the prompt. The tables
are generated by `bin/harness.mjs` from the golden records the runner checks
every trial against, so they are measured, not recalled. Only headings and
sizes are published. The records hold the full text and are not in this
repository.

## What the model is told about the operator

The account's email address reaches the model in every session, in the
`session_context` attachment listed above. It is `ksmith@centricle.com`, and it
is public. It appears in the published outputs of one run, the relay chain
`runs/html-chain-relay-low/`: at step 008 Haiku wrote it into a
`<meta name="author">` tag, and every later step carried it forward.

| What | Where it appears in this repository |
|---|---|
| The email address | 71 tracked files, all in `runs/html-chain-relay-low/`: 34 outputs and 37 transcripts |
| The username `ksmith`, as the owner column of `ls -l` output | 556 transcripts |
| The account's organization id | No published file. The CLI receives it, but it is never rendered to the model, and the runner drops it from the conditions it hashes. |

Published: every output file, every counted attempt's stream-json transcript
from the room, the tallies, the renders, the runner and the task definitions.

Not published: the transcripts of the harness replica, because the full user
configuration is in them; the transcript and output of any halted attempt,
which the runner sets aside untracked; the pilot's original desktop captures,
since the pilot's outputs are re-rendered like everything else; the golden
records; and anything the runner built from the operator's own instruction
files to check that the room held.

## Reproducing

The runner is bash and jq. The tally, the harness tables and the site are
Node 22. It expects:

- macOS. The room lives under `/private/tmp`, and the owner column in the
  transcripts' `ls -l` output is what macOS prints.
- The Claude Code CLI at the pinned version, signed in with an account. Every
  transcript records `apiKeySource: none`. A different binary makes a different
  golden record, so a rerun on a later CLI is a new campaign, not a repeat.
- `git`. The runner commits each run's rows and outputs as it goes, so it runs
  inside a clone.
- For renders, Google Chrome and `cwebp`. Renders only reproduce on the same
  Chrome build and fonts; `renders/README.md` names the build used.

```
bin/campaign.sh                                # campaign.tsv
bin/campaign.sh --campaign campaign-2.tsv
node bin/tally.mjs --summary                   # data/trials.csv, then the comparison tables
node bin/tally.mjs --campaign campaign-2.tsv   # data/campaign-2.csv
bin/render.sh -j 2
bash test/run-tests.sh tmp/test                # the runner against a stub CLI
```

`campaign.sh` first confirms the room on Haiku and writes that session's
conditions as the golden record; every later trial is checked against it. The
golden records and one full session record per run are archived to a directory
outside the repository, named at the top of `bin/lib.sh`. Rerunning the same
command resumes where it stopped.

The site:

```
cd site && npm ci && npm run dev
```

## An API arm, by pull request

The question the tables above leave open is how much of what these models do
is the model and how much is the harness. The way to answer it is a third
profile: the same tasks, the same seeds and prompts, through a bare Messages
API call with no system prompt. Pull requests that add one are welcome. One
should carry:

- A profile with its own name, `api`, next to `room` and `harness` in
  `bin/lib.sh`, or a sibling script that writes the same rows.
- Rows in `runs/<run>/trials.jsonl` with the existing columns, `profile` set
  to `api`, and the request itself (model id, parameters, the absence of a
  system prompt) hashed into `conditions_sha256`, so a reader can tell what
  the model saw.
- How the file tasks are handed over, stated. With no tools, the seed has to
  reach the model some other way, and the choice is part of the conditions.
- Outputs under `runs/<run>/NNN/`, and the tally rerun without changing any
  existing row.
